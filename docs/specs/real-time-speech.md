## Goal

Jarvis starts speaking while Gemma is still generating. Synthesis and playback overlap token generation, which runs on the other Pi. Success is measured as **time from Enter to the first audible word**, aiming for at most 3 s on a short question, with the target fixed after R0's baseline. A failure in one answer never silences later answers.

## Problem (observed 2026-11-06 on the Pi)

- Today the stages run one after another: the full text streams (7–16 s), then the whole answer is synthesized, then it plays.
- An 830-byte answer failed with `speech synthesis failed`, most likely because of the 30 s `SYNTHESIS_TIMEOUT`. The cause is hidden: the `Display` on `SpeechError` is hand-written and drops the source.
- `SpeechOutput::fail_operation` sets `self.disabled = true` permanently (`src/features/speech/output.rs`), so Jarvis must be restarted to get speech back.
- rodio prints `speech output configuration: DeviceSinkConfig {...}` into the prompt.

## Tickets

Each ticket lists the files it owns. Code tickets finish with the full verification list in AGENTS.md, including the Python worker test if speech changed.

### R0: measure latency
- Add to the run diagnostics: time to first streamed text, and time to first audio (when playback of an answer starts). Mark them `Unavailable` when not observed, never 0.
- On the Pi: measure Supertonic's real-time factor (synthesis seconds per audio second) for 3 sentence lengths. Measure Gemma's time to first token for a short and a long prompt.
- Output: the numbers in this spec's Status notes and `notes/SPEECH_LATENCY.md`.
- Owns: `src/features/assistant/run_observer.rs`, `run_report.rs`, `src/interfaces/cli/**`, and their tests. If time to first audio needs a signal from `features/speech/`, report the needed API instead of editing it (R1 owns that module).

### R1: speech recovery
- Replace the `disabled` bool with a state enum (S4). Derive errors with `thiserror` and `#[source]`, so the CLI warning shows the cause chain. On a failure, terminate the worker and start a fresh one on the next answer. After 3 consecutive failures, move to `Disabled` with a notice. A success resets the count.
- Silence or redirect rodio's device-configuration print.
- Tests: recovery after one failure, disabled after the third consecutive failure, and a success between failures resets the count (a boundary table for 2/3/4).
- Owns: `src/features/speech/**` (except a new `chunker.rs`) and `tests/unit/features/speech/**`.

### R2: chunker
- A pure, incremental chunker: push streamed text deltas in, get speakable chunks out, and flush the rest at the end. Rules are S5. It handles abbreviations and decimals ("Dr.", "3.5") without splitting, and Markdown that the speech cleanup already strips.
- Tests: a table covering 39/40/41 characters for the first chunk, 300/301 for the force split, sentence and clause boundaries, and deltas split mid-word.
- Owns: `src/features/speech/chunker.rs` and `tests/unit/features/speech/chunker_tests.rs`, plus its `mod` line in `src/features/speech/mod.rs`.

### R3: streaming pipeline
- Wire the turn stream into the chunker, a bounded queue, the worker and gapless playback (S6). `/stop` and a new prompt clear everything. Time to first audio comes from R0's diagnostics.
- Pi acceptance: Darren hears speech start while the text is still streaming; a long story plays fully; `/stop` cuts it off.
- Owns: decided when R1 and R2 land.

### R5: Piper voice
- **R5a:** `scripts/tts/piper_worker.py`, the same JSON frames as `supertonic_worker.py` (ready, speak with `output_path`, completed or error), with the model loaded once. Plus a pinned setup script and Python tests mirroring the Supertonic worker tests. Owns `scripts/tts/piper*` and `tests/unit/features/speech/piper_worker/`.
- **R5b:** config (`src/config/tts.rs`) chooses the Piper or Supertonic worker and the voice; playback accepts the worker's sample rate (rodio resamples); rename Supertonic-specific Rust naming only where it is now generic. Pi acceptance by ear.

### R4: voice decision
- If R0's real-time factor is at most about 0.5, keep Supertonic and close this ticket. Otherwise, compare Piper on the Pi for speed and quality, judged by Darren.

### R7: keep the history in Gemma's prompt cache
- Send recalled memories as one user message placed **after** the history and directly before the new prompt, instead of through Rig's `.documents()` (which Rig 0.42 puts before the history). Each memory reads exactly as it does today (the same `Document` text). No recall means no extra message.
- The memory message stays run-local: it is never part of the batch appended to session history, the archive, or the "forget that" focus.
- Expected effect: each turn reprocesses only the last exchange, the new memories and the prompt; older history comes from the cache. Pi acceptance: `cached_input` grows with the conversation instead of staying at about 271, and first_text drops on the third and later turns.
- Tests (Wiremock SSE, the production streaming path): the request's message order with and without recalled memories; the stored history after a run contains no memory text; two consecutive runs share the whole earlier history as a request prefix.
- Owns: `src/features/assistant/**`, `src/features/conversation/**` if the history hand-off needs it, and their tests.

### R7b: memories before the last exchange
- Darren's decision (2026-11-07), after R7's position made Gemma copy a recalled wrong answer. Place the recalled-memory message (built exactly as R7 builds it) before the **last whole exchange** in history: `[system, older batches, memories, last batch, prompt]`. With no history, it goes directly before the prompt; with no recall, no message is added.
- Use the history's batch boundary, never a message count: an exchange with a tool call has four messages. Only `features/conversation` knows the batches, so it hands the assistant the history already split (or the full request history), and the assistant stays unaware of batches.
- Unchanged: the memory never enters stored history, the archive, or the forget focus; the wire text of each memory is the same.
- Tests: the request order table (no history, one batch, two batches, and the last batch being a tool-call exchange); the stored history holds no memory text; across two runs the request prefix up to the older batches is identical.
- Pi acceptance: Darren's five-question conversation; "a famous food from there" answers about Tokyo; `cached_input` still grows across turns.
- Owns: `src/features/assistant/**`, `src/features/conversation/**`, and their tests.

### R6: speech diagnostics display
- Today `run_input_loop` (`src/interfaces/cli/repl/mod.rs`) prints `Speech diagnostics: time_to_first_audio=...` with `eprintln!` once speech ends. By then the `You> ` prompt is often already shown, so the line lands after `You> ` or in the middle of what Darren is typing, and nothing says which answer it belongs to.
- Wanted: the line always starts on its own line, names the answer it belongs to (for example `Speech diagnostics (previous answer): ...`, or the first words of the answer), and the prompt is shown again afterwards when it was visible. Typed-but-unsent input is the terminal's, so keep it simple: start a new line and redraw `You> `.
- The presenter already tracks `prompt_open`; use it rather than a second flag. A notice printed while a prompt is open goes through the presenter.
- Tests: the output for a prompt that is not visible, a prompt that is visible, and an unavailable first audio.
- Owns: `src/interfaces/cli/**` and `tests/unit/interfaces/cli/**`.
